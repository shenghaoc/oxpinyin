## Summary

- **Cold load, zhuyin `journals`, wall:** ox/pin **0.529** (95% paired
  bootstrap 0.498–0.552). This is the only one of the 32 load, init,
  first-candidate and full-lifecycle timing figures whose same-bytes
  control passes the §7.5 rule
  (`docs/findings/tooling-consolidation-python-just.md`).
- **Every other cold timing figure is INCONCLUSIVE.** The control/ox
  interval leaves 0.95–1.05, so the tool prints no pin ratio. Load,
  init and first candidate are INCONCLUSIVE in every other cell.
  The host is a 4-CPU cloud VM (below), which is the likely
  cause. This run does not establish cold init or first-candidate ratios.
- **Major page faults are deterministic.** Each count had zero spread over
  60 samples. Load: ox 11, pin 22 (pinyin) or 25 (zhuyin). Init: ox 30
  (pinyin) or 26 (zhuyin), pin 19. First candidate: ox 0, pin 3 (pinyin)
  or 1 (zhuyin). Full lifecycle: ox 50 or 48, pin 46 or 45.
- **Init's extra faults come from the facade.** Init takes 26–30 major
  faults for ox against the pin's 19. Measured with per-file `mincore`
  before and after init, the only file that gains more resident pages for ox
  is the ox library itself: +118 pages against the pin's +71 (pinyin) and
  +106 against +52 (zhuyin). libdb, the system data and the profiles gain
  the same pages on both sides.
- **Every sample was evicted and verified.** 1,140 eviction records, 43,700
  file checks, all on ext4. No page stayed resident after advice or at the
  final check before launch, and no sample was refused.

the host's libdb 5.3, GLib 2.80, libpcre2 and libstdc++.

**Other activity.** Nothing else heavy ran. `dockerd` and `containerd` (left
by setup and the build) were idle. The 1-minute load average was 0.90 just
before the campaign.

## Cold set

`--teardown-cache cold` evicts, before every timing and memory sample, the
facade library, its `DT_NEEDED` closure outside the C runtime, every
system data file and the sample's private restored profile.

**`libgcc_s` stays warm, for every side.** The controller's managed CPython
maps `/usr/lib/x86_64-linux-gnu/libgcc_s.so.1`, and its `uv` launcher links
it. DONTNEED cannot evict a page that a process maps, so every sample whose
closure reaches it would be refused. On the maintainer's ruling,
`libgcc_s` joined the C-runtime set (`teardown.py`, `C_RUNTIME`). glibc and
its loader were already in that set.

Closure evicted per side (from the cold mode's own resolver,
`teardown.library_dependencies`):

| side | libraries evicted besides the facade |
| --- | --- |
| ox, control | libdb-5.3.so, libglib-2.0.so.0.8000.0, libpcre2-8.so.0.11.2 |
| pin | libdb-5.3.so, libglib-2.0.so.0.8000.0, libpcre2-8.so.0.11.2, libstdc++.so.6.0.33 |

**Preflight.** Before the run, `/proc/*/maps` of every process was scanned
for those 31 files: both facades of each side, the libraries above and
the 23 system data files. No process mapped any of them.

## Where init's major faults come from

`ru_majflt` is a process total, not per file. To attribute init's 26–30
faults against the pin's 19, cold memory samples read every cold file's
resident pages with `mincore` at M0 (after load, before init) and at M1
(after the workload). The tool's `residency` record reports them (tools at
f8aa567). Between M0 and M1 the subject takes no major fault outside init.
The pin takes 1 (config) plus 3 (pinyin) or 1 (zhuyin) in first candidate.

Command: the campaign command above with `--teardown-stage pilot
--teardown-cache cold`, run 12:14:59Z–12:15:31Z on the same host, binaries,
data and profiles. That gives three memory samples per side per cell. All
four cells were COMPARABLE, and every count below was identical in all
three samples. The raw record stream was not kept: it lived only in this
disposable cloud container.

Resident pages, M0 → M1 (file size in pages), for both profiles unless stated:

"Other system data" is `gb_char.bin` (0 → 726, the whole file),
`gbk_char.bin` (0 → 85), `opengram.bin` (0 → 201), `merged.bin` (0 → 8),
`pinyin_index.bin` (0 → 15), `bigram.db`, `phrase_index.bin`, `punct.bin` and
`addon_phrase_index.bin` (0 → 4 each), and `table.conf` (0 → 1). For zhuyin,
both addon files and `punct.bin` stay at 0 on both sides. The profile files gain the same pages on
both sides, for example `gb_char.dbin` 0 → 115 with `phrases` and 0 → 35 with
`journals`.

Both sides map the same data files with the same resident size at M1. This
is from the same samples' smaps groups in the `memory-deltas` record:
`gb_char.bin` 2,904 KiB, `gbk_char.bin` 340 KiB, `opengram.bin` 804 KiB and
`merged.bin` 32 KiB. The pin maps them writable (private); the subject maps
them read-only, plus a 320 KiB writable `gb_char.bin` mapping.

**Reading.** Only one file gains more pages during init for ox than for
the pin: the ox library itself, by 47 more pages (pinyin) and 54 (zhuyin).
That makes the ox library's text and read-only data the likely source of
the extra 7–11 init faults. This is an inference: a fault reads a readahead
window, and pages read with `read()` count no fault. The pin's pinyin init
brings in 96 more pages of `addon_pinyin_index.bin` and still takes fewer
faults. The subject's 128 resident facade pages at M0 are what `dlopen`
faulted in during load. Init then touches functions and tables that load
did not.

## What this does not show

- Cold init and first-candidate ratios. They need a quieter host. Rerun the
  same `confirm` command on a dedicated machine.
- glibc, its loader and `libgcc_s`, which stay warm for every side.
- Device latency. `/dev/vda` is a virtual disk, so cold reads can be served
  by the hypervisor's cache. The fault counts do not depend on that; the
  timings do.
